# INGEST-001 — framework-wide embedding compatibility council

The maintainer requests a new, single read-only council pass after the
embedding-pool compatibility amendment. This authorization is separate from the
completed rounds1–4. The exact current REM is the review target; code has not
implemented it. The review must discover all maintained direct and indirect
embedding consumers across the framework, including consumers the REM does not
name. Its named paths and DI rows are a lower bound, not a closed audit universe.

Evaluate both unchanged pre-existing configuration and an explicitly selected
replacement embedding model operating against a fresh compatible memory
namespace. Distinguish model-space/data incompatibility from subsystem/API/config
regression. Same-dimension different model/preparation must not be treated as
compatible. The operator must provision a fresh coherent vector/graph/WAL layout;
no clearing, migration, re-embedding or personal-store access is authorized here.

Reviewers independently trace constructors, pool/default/explicit bindings,
query/document roles, precomputed/provided vectors, caches, indirect storage,
raw store clients, dimension assumptions and lifecycle/background/exit paths.
Do not assume all modules with no embed_* call are unaffected: follow shared
protocol/config/store contracts and already stored-vector comparisons. Classify
active, public-unwired and inactive/example routes accurately. Any newly found
subsystem needs a source-backed disposition: compatible unchanged; covered by a
narrow declared contract/test update; or an actionable design gap. No speculative
architectural rewrite or unsupported claim of runtime compatibility is requested.

Demand operational baseline compatibility, not YAML parse-only success. New
optional fields may resolve from qualified artifact-bound readiness. No silent
model switch, default rebinding, arbitrary metadata guesses, ignored failures or
unguarded legacy lane. Missing baseline readiness is a readiness stop requiring
maintainer disposition, not success. New-model proof is future work explicitly
specified by the design, not a model install or inference request in this review.

The report must include an independently sourced framework-wide consumer matrix,
any uncovered subsystems/paths/tests, exact acceptance/negative-proof requirements
for unchanged configuration and model replacement, numbered findings, a criterion
matrix and an honest /10 score. Preserve prior review isolation: no peer verdicts
or unfiltered aggregate diffs, no inherited builder reasoning, private external
outputs only. The three reviewers receive the same request and boundaries.
