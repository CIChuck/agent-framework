# Friday Framework - Component Specifications: Batch 2a

**Focus:** Context Engineering Framework & Adapter Architecture

Definition:

Context Engineering in Agentic Architectures is the systematic process of curating, optimizing, and structuring the information available to an Agent at any given inference step. It bridges the gap between infinite storage (Memory) and finite attention (Context Window). It encompasses:

1. **Session State:** Managing continuity across turns and agents.
    
2. **Memory Lifecycle:** The continuous cycle of Extraction, Consolidation, and Retrieval.
    
3. **Prompt Architecture:** The physical structuring of tokens to maximize instruction adherence.
    
4. **Provenance:** Tracking the lineage of information to ensure explainability.
    

## 1. The Context Engineering Adapter (The "Swappable Brain")

Classification: Red (Framework)

Goal: To provide a standard Protocol (Interface) that allows different Context Engineering strategies to be "snapped" into the Agent. This abstraction ensures the underlying Memory Architecture is decoupled from the strategy used to process it.

### 1.1. Interface: `ContextEngineeringInterface` (Protocol)

This adapter defines the standard lifecycle methods that _any_ context strategy must implement.

```
```
class ContextEngineeringInterface(ABC):
    """
    The Master Protocol for Context Engineering. 
    Implements the lifecycle defined in 'Google Context Engineering'.
    """

    # --- Session Management ---
    @abstractmethod
    async def initialize_session(self, session_id: str, user_id: str) -> 'SessionState':
        """Loads or creates the session context, establishing the 'Thread'."""
        pass

    # --- NEW: Recovery Cycle ---
    @abstractmethod
    async def restore_checkpoint(self, session_id: str, turn_id: str) -> 'SessionState':
        """
        Reverts the session state to a previous turn.
        1. Triggers MemoryController.rollback_session()
        2. Reloads the SessionState effective at that time.
        """
        pass

    # --- The Ingestion Cycle (Extraction) ---
    @abstractmethod
    async def extract_context(self, 
                              interaction_turn: 'Interaction', 
                              async_execution: bool = True) -> None:
        """
        Analyzes the last turn to identifying 'Hot' facts or memories.
        Triggers 'Memory Generation' (Extraction) tasks.
        """
        pass

    # --- The Maintenance Cycle (Consolidation) ---
    @abstractmethod
    async def consolidate_memory(self, session_id: str) -> 'ConsolidationReport':
        """
        Merges fragmented short-term memories into solidified long-term blocks.
        Resolves conflicts and summarizes 'drift'.
        """
        pass

    # --- The Retrieval Cycle (Construction) ---
    @abstractmethod
    async def assemble_context(self, 
                               query: str, 
                               state: 'SessionState', 
                               budget_limit: int) -> 'ContextPayload':
        """
        The core 'Recall' step. 
        Selects, Ranks, and Compresses data into the Context Window.
        
        **Active Search Support:** The `query` parameter supports 'Active Search' patterns (Memory-as-a-Tool).
        It may differ from the user's last message (e.g., a synthesized query like 
        "Find Python error logs from last week" generated by the Agent).
        """
        pass

    # --- The Formatting Cycle (Architecture) ---
    @abstractmethod
    async def format_prompt(self, 
                            system_prompt: str, 
                            payload: 'ContextPayload') -> List[Dict]:
        """
        Physically arranges the messages (System, Tools, Context, User) 
        to optimize for the specific model's attention span (Start/End bias).
        """
        pass
``````

## 2. Core Component: `ContextAssembler` (Default Implementation)

Classification: Red (Framework)

Role: The standard implementation of ContextEngineeringInterface for the Friday Copilot.

### 2.1. Implementation & Docstring

```
class ContextAssembler(ContextEngineeringInterface):
    """
    Standard assembler for the Friday Copilot. 
    Implements rigid token budgeting and active search capabilities.
    """
    
    async def assemble_context(self, query: str, state: 'SessionState', budget_limit: int) -> 'ContextPayload':
        """
        Executes the 'Recall' step with support for both Passive and Active retrieval.
        
        Args:
            query: The search string.

                   - In 'Active' mode (Memory-as-a-Tool), this is an Agent-generated query 
                     (e.g., "Find error logs from yesterday").
            state: Current session state.
            budget_limit: Calculated token ceiling (Dynamic_Limit).
            
        Returns:
            ContextPayload: A strictly budgeted object containing relevant Passages, Entities, and Facts.
        """
        pass
```

### 2.2. Feature: Context Budgeting (The "Knapsack")

The Assembler manages the **Context Budget** using rigid prioritization logic.

**The Handshake (Budget Calculation):**

1. **Calculate Fixed Costs:** `Fixed_Cost = len(System_Prompt) + len(Tool_Definitions) + Output_Buffer`
    
2. **Determine Available Budget:** `Dynamic_Limit = Model_Max_Tokens - Fixed_Cost`
    
3. **Request Retrieval:** Call `MemoryController.recall(..., token_limit=Dynamic_Limit)`
    
    - _Critically, this happens BEFORE content generation to prevents overflow._
        
4. **Final Assembly:** Assemble the prompt. If `recall` returns slightly more (due to fragmentation), apply final pruning.
    

**Equation:** `Total_Context = System + Tools + Output_Buffer + (Dynamic_Content)`

**Priority Hierarchy (Drop Order):**

1. **Deep History (Lowest):** Turns 10+ ago.
    
2. **Scoped State:** 'app:' vars (Low), 'session:' vars (High).
    
3. **Weak Matches:** Vector passages with low `similarity`.
    
4. **Recent History:** Turns 3-10.
    
5. **Immediate Context (Critical):** Last 2 Turns, User Query, 'user:' scoped vars.
    

### 2.3. Feature: Active Search Scenarios (Memory-as-a-Tool)

_Ref: Google Context Engineering > Memory-as-a-Tool_

The `assemble_context` method is designed to support two distinct retrieval scenarios. The Agent (via Tool usage) can explicitly trigger Scenario B.

**Scenario A: Passive Context Loading (Default)**

- **Trigger:** User sends a message.
    
- **Query Source:** The raw user input (e.g., "Why is it broken?").
    
- **Behavior:** The Assembler performs a broad search to find generally relevant history and facts to "prime" the model.
    

**Scenario B: Active Search (Memory Tool Usage)**

- **Trigger:** The Agent determines it lacks specific information and calls the `recall_memory` tool.
    
- **Query Source:** A precise, Agent-generated string (e.g., "Python syntax error list for file:main.py").
    
- Behavior: 1. The Agent pauses generation.
    
    2. assemble_context is called with the specific query.
    
    3. The Assembler narrows the search scope (e.g., strictly filtering by file:main.py).
    
    4. The result is injected as a "Tool Output" rather than general context.
    

### 2.4. Feature: Memory Provenance (Lineage)

_Ref: Google Context Engineering > Memory Provenance_

Every item injected into the context must carry **Lineage Metadata**. The Assembler ensures no "Magic Context" exists—every token must have a source.

- **Implementation:** The `ContextPayload` items must include:
    
    - `source_id`: UUID of the origin document/turn.
        
    - `extraction_method`: e.g., "VectorSearch", "UserExplicit", "HeuristicExtraction".
        
    - `confidence`: Float (0.0-1.0).
        

## 3. Component: `MemoryExtractor` (The "Harvester")

Classification: Blue (Capability)

Ref: Google Context Engineering > Memory Generation: Extraction

**Goal:** To parse the live conversation stream and identify candidates for memory _before_ they are forgotten.

### 3.1. Strategies

The adapter allows plugging in different extraction strategies:

1. **Named Entity Extraction (NER):** "User mentioned 'Project Alpha'."
    
2. **Task State Extraction:** "User completed task 'Fix Bug'."
    
3. **Sentiment/Preference Extraction:** "User expressed frustration with Python."
    

### 3.2. Asynchronous Triggering

_Ref: Google Context Engineering > Background vs Blocking Operations_

- The `extract_context` method typically runs **Asynchronously** (via the Event Bus) after a turn completes.
    
- **Blocking Mode:** Can be forced for critical "Safety Context" updates.
    

## 4. Component: `MemoryConsolidator` (The "Synthesizer")

Classification: Blue (Capability)

Ref: Google Context Engineering > Memory Consolidation

**Goal:** To prevent Context Fragmentation. Short-term observations must be merged into cohesive Long-term facts.

### 4.1. Consolidation Logic

1. **Deduplication:** Merging "The API Key is 123" and "Key: 123" into one Graph Node.
    
2. **Summarization:** Compressing a 20-turn debugging session into a single "Episodic Summary" stored in the Vector Store.
    
3. **Conflict Resolution:** If Turn 1 says "My name is Bob" and Turn 50 says "My name is Robert", the Consolidator updates the Entity Property `name` (with lineage tracking).
    

## 5. Component: `PromptArchitect` (The "Layout Engine")

Classification: Red (Framework)

Ref: Google Context Engineering > Inference with Memories

**Goal:** To structure the final prompt to combat "Lost in the Middle" and optimize for "System 2" reasoning.

### 5.1. Layout Strategy (Default)

1. **System Block:** Identity & Guardrails.
    
2. **Transparency Block (New):** "Recent Memories: [System auto-archived 'User hates red']". (Injected from `ContextPayload.recent_memories`).
    
3. **Procedural Memory:** "Here is how you successfully solved similar tasks in the past:" (Few-shot examples).
    
4. **Semantic Memory:** "Relevant Documentation passages:" (Vector).
    
5. **Episodic Memory:** "Conversation History:" (Last N turns).
    
6. **State Memory:** "Scoped Variables:" (User prefs, Env state).
    
7. **User Trigger:** The Query.
    

## 6. Acceptance Criteria for Batch 2a

1. **Test: Scoped State Enforcement**
    
    - _Action:_ `state.set_var("invalid:key", 1)`.
        
    - _Result:_ Raises `ValueError`.
        
    - _Action:_ `state.set_var("user:theme", "dark")`.
        
    - _Result:_ Success.
        
2. **Test: Checkpoint Restoration**
    
    - _Action:_ `restore_checkpoint(session_id, old_turn_id)`.
        
    - _Result:_ Session history is truncated, and `SessionState` reflects the old state.
        
3. **Test: Token Budget Hard Cap**
    
    - _Input:_ 100 relevant documents (Total 10k tokens).
        
    - _Budget:_ 2k tokens.
        
    - _Result:_ The `assemble_context` method returns < 2k tokens. It explicitly drops "Low Priority" items (defined in hierarchy) and logs a `ContextPruningWarning`.
        
4. **Test: Extraction Trigger**
    
    - _Action:_ User says "My API key is XYZ".
        
    - _Verification:_ The `MemoryExtractor` fires (async), and a new Graph Node `Secret` is created with proper `provenance` pointing to the interaction ID.
