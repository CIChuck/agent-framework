## Required findings, in priority order

### CDR-001 — Medium: the listed verification profile omits the repository minimum broad gates

**Evidence:** `docs/planning/active/friday-telemetry-rewire/directives/CD-001-local-telemetry-assembly.md:93-105` requires focused and two-package pytest, changed-file Ruff, and broader tests only if coupling is discovered. `docs/reference/policies/repository-engineering-policy.md:194-204` identifies `uv run ruff check .`, `uv run pytest`, and affected-scope mypy as the minimum relevant validation gates, and additionally requests package validation for boundary changes. `AGENTS.md:101-109` names the broad checks and explicitly requires reporting unrelated legacy failures plus meaningful narrow validation. The directive changes a public shared provider's span, mutation-isolation, and failure behavior (`CD-001:67-69,82-83`), so the repository gate remains relevant. Its own precedence places repository policy above the directive (`CD-001:15-19`).

**Problem and impact:** A builder following only the directive's executable list can finish and freeze a candidate without attempting either broad gate. Conditional expansion is weaker than the higher-level requirement. A validator then has to invent additional required commands or accept an incomplete verification profile, undermining AC-06 and reproducibility. This finding does not assert that broader checks currently pass or that every root-discovered test is safe to execute.

**Bounded correction:** Reconcile the required command list with the higher-level gates. Include repository Ruff and a defined, safe deterministic repository pytest profile, with exact preapproved exclusions if root discovery contains real-data or external-effect tests. Where a gate cannot safely execute under the directive's no-external-effect restriction, record the specific conflict and obtain the appropriate bounded authority decision instead of silently treating package suites as equivalent. Record before/after failures and distinguish unchanged baseline failures from regressions; do not let a nonzero command become a claimed pass or an implicit waiver. Retain the listed focused/package checks.

**Verification / documentation impact:** AC-06 and T01-06 need the reconciled command profile; the frozen request and implementation-report template must carry commands, exclusions, results, and baseline evidence. No product-file expansion is required by this correction. Broader runtime execution is not authorized by this review.

### CDR-002 — Medium: Python 3.13 checking alone does not enforce the declared Python 3.10 compatibility contract

**Evidence:** `CD-001:96` fixes affected-source mypy at `--python-version 3.13`. At the preparation base, `packages/friday-chat/pyproject.toml:6` and `packages/friday-telemetry/pyproject.toml:6` both declare `requires-python = ">=3.10"`; root `pyproject.toml:125-132` sets mypy's target to 3.10. `CD-001:45-49` excludes dependency metadata and templates, and `CD-001:53-55,79-85` requires compatibility and forbids typing relaxation. Repository engineering policy requires compatibility across dependent packages (`repository-engineering-policy.md:5-12`), meaningful source typing (`87-100`), and explicit migration/contract handling (`74-81,181-192`).

**Problem and impact:** The explicit 3.13 override does not detect Python 3.11–3.13-only type/API use introduced into files that still advertise Python 3.10 support. Installed-interpreter checking and supported-minimum checking establish different facts. The directive has no minimum-version compatibility check, identified exclusion, or authorized change to the supported version. A green listed command could therefore support AC-06 while leaving a supported deployment unable to import or use the new observer/composite implementation.

**Bounded correction:** Retain 3.13 checking if needed for the installed environment, but add a meaningful check for the changed source against the advertised supported minimum. Prefer the repository's 3.10 mypy target plus a targeted syntax/API compatibility check; separate preparation-base debt from introduced failures. If existing dependencies make the full minimum-version check impossible, specify the exact limitation and narrowly valid alternative evidence or obtain a scoped maintainer waiver. Do not silently raise the package minimum or change out-of-manifest metadata.

**Verification / documentation impact:** AC-06 must distinguish installed-environment typing from advertised-version compatibility. Freeze both commands and baseline limitations in the request. This is a directive-profile correction, not a claim about syntax in the current implementation.

## Advisory contract clarifications

These are ambiguities worth tightening; they are not independent assertions of a violated mandatory requirement and are not the basis of the verdict.

- **CDR-A001 — Partial span-start failure timing.** `telemetry-contract.md:58-74` requires retaining opened child spans, cleaning recorded children, and raising after fan-out. The public `TelemetryInterface.start_span` only returns a string (`packages/friday-telemetry/src/friday_telemetry/interface.py:40-50` at the preparation base). Explicitly state that, when start raises after partial success, rollback attempts occur before raising, since the caller otherwise has no returned composite ID. Clarify that exactly-once failure handling means one cleanup attempt per successfully recorded child, with cleanup failures included categorically; arbitrary sink behavior cannot guarantee a successful end. Add a mixed healthy/failing start test that proves all sinks were attempted, rollback was attempted, no unreachable mapping remains, and no exception content escapes. The existing words "clean up each recorded child" can reasonably be read to require this already.
- **CDR-A002 — Observer span admissibility.** `CD-001:56-69` uses the three-method `TelemetryInterface` and separately requires composite nested-span correctness, while `telemetry-contract.md:31-54` fixes first-slice event admission without fixing an observer span-name/end-data schema. State whether observer span calls are visibly rejected/deferred in this slice or accepted through a closed schema. Composite's general provider-neutral API can remain general; the Chat boundary must maintain `telemetry-contract.md:45-47` privacy. Add sentinels in span names, parent/span IDs, and end-data to the relevant negative coverage if observer spans are admitted. This avoids a validator conflating direct composite span tests with lifecycle-observer coverage.
- **CDR-A003 — Mixed lifecycle outcomes.** The lifecycle truth rule (`telemetry-contract.md:37-40`, `tactical-plan.md:21`) is clear, but a compact outcome table would help for cancellation followed by cleanup failure, start/banner failure, and failures swallowed by existing maintenance/coordinator helpers. Preparation-base `app.py:249-260,542-576` already catches failures; truthful diagnostics must observe those without changing application outcomes. Require stage-failure and cancellation combinations, not only a successful exit and a top-level exception.
